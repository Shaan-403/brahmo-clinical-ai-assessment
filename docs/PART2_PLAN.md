# BRAHMO — Part 2: Plan to a Production Clinical AI

_Single markdown document, as long as it needs to be and no longer. Diagrams welcome._

## 1. Completion architecture

### What we have now

**Data layer.** SQLite, single file, single-writer connection (`src/db/connection.py`), numbered plain-DDL migrations (21 of them, no SQLite-specific syntax by deliberate choice). Holds a 2,000-row CDCI subset (160 FDCs decomposed), 63 NLEM rows, 50 Jan Aushadhi rows, 783 pharmacy-stock rows, 15 severe-interaction pairs, 12 regulatory events, and 4 STW PDFs chunked into 49 decision units. Every ingestion loader is idempotent via content-hash (`load_batches.file_hash`), and every row carries `load_batch_id` back to a specific ingestion run.

**Normalization + ambiguity handling.** Exact-normalized-brand-name matching only, zero fuzzy auto-accept. Anything not uniquely resolvable — 597 items across 5 reason codes on this data pack — lands in `review_queue`, an inert SQL table with no UI, no assignment, no SLA tracking, and no feedback loop (resolving one queued item today doesn't stop the same name being re-queued on the next ingestion run).

**Safety rail.** Four deterministic checks (duplicate ingredient, prohibited/restricted FDC, severe interaction, cumulative exposure), pure lookup logic, 8-state contract, called synchronously in-process against the one SQLite connection. No LLM in this path at all — by design, and that stays true regardless of scale.

**Regulatory status.** Event-sourced (`regulatory_events`, effective-dated, supersession-aware) rather than a boolean — this part of the design already scales conceptually, it just needs a real ingestion feed instead of a static CSV.

**Module B (Q&A) retrieval.** Hybrid — SQLite FTS5 `bm25()` for lexical, paired with a *fallback* semantic backend, not the intended one. The design (`DESIGN.md` D-016) always intended `fastembed` (ONNX-based local embeddings) for the semantic leg; in this development environment `fastembed`'s model download is blocked by egress policy, so the system automatically and visibly falls back to a deterministic offline TF-IDF cosine backend instead, and reports which backend ran. TF-IDF was the backend that could actually be built and tested end-to-end here — it is not the production semantic design, just the one this environment allowed us to prove out. Retrieval-and-quote only either way, no generation, no LLM anywhere in the answering path. Corpus is 4 conditions, 49 chunks, rebuilt in-process on every ingest.

**Module C (integration).** A CLI script, not a service. No HTTP layer, no auth, no multi-tenancy concept anywhere in the schema (no `tenant_id`/`clinic_id` column exists). One process, one connection, one prescription at a time.

**What's structurally absent, not just small:** no patient-context field anywhere (age, weight, renal/hepatic status, pregnancy, allergies — none of this exists in the schema, so today's rail is prescription-only, not patient-aware, despite BRAHMO's stated goal); no serving layer of any kind; no freshness/re-evaluation mechanism (binding law 10 — "no silent upgrades" — isn't violated today only because nothing ever updates in place); no audit log beyond raw table rows; no concurrency control beyond SQLite's own single-writer lock.

### What must change for production, and why

**1. SQLite → Postgres.** *Why:* SQLite's single-writer model is the first wall — one concurrent ingestion run (a new gazette notification, a pharmacy re-upload) serializes against every doctor's read at that moment. At 100 simultaneous doctors this isn't a tail-latency problem, it's a correctness/availability one. The migrations are already portable plain DDL (deliberate choice, see `SCALE.md`), so this is a lift-and-shift, not a redesign — genuinely the cheapest item on this list.

**2. CLI → a real service boundary with scalable concurrency.** *Why:* `src/module_c/trace.py` is intentionally thin and synchronous — fine for one prescription proving integration, unusable for 100 doctors hitting it concurrently. Production needs a stateless request-handling boundary (an HTTP/RPC entry point) that can scale horizontally behind a load balancer, since the checks and retrieval logic underneath are already pure functions over a connection and port cleanly. This does **not** automatically mean a message queue in front of every request — the rail checks and retrieval are fast, synchronous lookups today, and a queue adds latency and operational surface that only pays for itself if a measured latency/SLO requirement demands request buffering, backpressure, or async processing (e.g. a slow ingestion-triggered re-evaluation job). The concurrency boundary should be sized and chosen against real load-test numbers, not assumed up front.

**3. Patient context as a first-class schema concept — for safety gating, explicitly not for dosing.** *Why:* Right now "patient-aware" is aspirational — there's no age, weight, renal function, pregnancy, or allergy field anywhere, and several real contraindication checks a doctor would expect (e.g. a drug that's fine generally but contraindicated in pregnancy or renal impairment) simply can't exist without it. This is a hard boundary, not a phase-2 nuance: patient context is required so the safety rail can gate/flag against patient state, and it must **never** be used to calculate or suggest a patient-specific dose (weight-based mg, renal-adjusted dose, etc.) — that fence is binding in Part 1 (no patient-specific dose calculator, confirmed structurally via the AST-level guarantee that no arithmetic touches Module B's answer text) and stays binding as patient data is added, not something scale is allowed to erode.

**4. Review queue → an actual triage surface.** *Why:* 597 open items from a 2,000-row subset. A national catalog will produce a review queue in the tens of thousands (`SCALE.md`'s own estimate). An internal SQL table nobody works is equivalent to silently dropping that data from the drug master forever — functionally adjacent to the "unchecked state rendered as safe" auto-fail condition, just one layer removed. This needs a queue with assignment, SLA, and the alias-feedback loop (`gaps_register.md` #5) so a human resolving "Zinc Sulphate" once doesn't force every future ingestion to re-ask the same question.

**5. Real embeddings instead of the TF-IDF fallback.** *Why:* `fastembed` was always the intended semantic-retrieval path (D-016) and was never actually exercised in this build — only its offline TF-IDF fallback was, because the model download was blocked in this development environment. TF-IDF is brittle to vocabulary drift and won't generalize the way a real embedding model does as the corpus grows from 4 conditions to a real national STW/specialty set. Production has no such network restriction, so this is "turn on the path that was designed but untested," not a redesign — though it does mean the retrieval quality actually measured in Part 1 (11/11 on the mini-eval) was measured against the fallback, not the intended backend, and should be re-validated once `fastembed` is live.

**6. A freshness/re-evaluation mechanism.** *Why:* Binding law 10 ("no silent upgrades — a model, prompt, or data change triggers re-evaluation before it serves") is currently satisfied only by accident — nothing changes in place today. The moment gazette notifications or corpus versions update in production, gap #6 in `gaps_register.md` becomes live: an old `AUTO_RESOLVED` product resolution or a cached rail result could go silently stale. Production needs an explicit "new data version → what depends on it gets re-evaluated before serving" pipeline, not just an append-only table.

**7. Multi-tenancy.** *Why:* Zero tenant/clinic separation exists in the schema today — every table is implicitly single-tenant. Even a modest pilot across a few clinics needs row-level tenant scoping before any concurrent-access testing is meaningful, and retrofitting it after data exists is much more expensive than designing it in from the first production schema.

**8. Audit trail as a queryable, tamper-evident layer, not just raw rows.** *Why:* `rail_check_results` and `rag_answers` are append-only today (a good foundation — binding law "everything versioned, everything replayable" already holds structurally), but there's no audit *view*: no way to answer "show me every check run against this doctor's prescriptions in the last 30 days" without a raw SQL query. Production compliance/audit needs this as a designed surface, not an afterthought query.

Sequencing note (elaborated in §2): Postgres and the service boundary are the load-bearing changes everything else sits on top of; patient context and the review-queue UI are the ones that change what the product can actually promise a doctor; real embeddings, freshness, multi-tenancy, and audit are the ones that turn "works in a demo" into "safe to leave running."

## 2. Week-by-week plan (3–6 weeks, binary gates per week)

**Duration: 6 weeks (upper end of the allowed range).** Part 1's own gaps register lists 13 real, dated anomalies, and several of the production changes from §1 — contraindication-rule specification and approval, corpus sourcing, multi-tenancy adversarial review, real-embedding re-validation — are gated by clinical and security judgment, not engineering throughput. AI-first development compresses the code-writing time, not the time a doctor needs to specify and approve a safety rule or a security review needs to try to break tenant isolation. Compressing to 3 weeks would mean cutting exactly the verification steps whose absence the brief's own scoring punishes hardest (confidently-wrong = −1 on the held-back set generalizes directly to confidently-wrong in production).

**Team shape (small, deliberately):**
- **Tech Lead / Staff Engineer** (full-time) — drives the AI coding agents, reviews every generated diff, owns architecture and fence decisions (e.g. the no-dosing boundary).
- **Clinical SME**, a practicing doctor (~20% time) — owns every clinical judgment call: contraindication-rule specification and approval, corpus source vetting, review-queue triage policy, comparison-harness blinding design.
- **DevOps/Data engineer** (~30–50% time) — Postgres/infra provisioning, row-level security, load-test infrastructure, data-licensing logistics.
- **AI coding agents** do the bulk of implementation under the Tech Lead's review — this is what makes a 2.5-person team plausible at all for this scope.

### Week 1 — Postgres cutover + service boundary + patient-context schema (no logic yet)
**Deliverables:** all 21 Part-1 migrations ported and replaying cleanly on Postgres; a stateless HTTP wrapper around `build_trace()`; a `patient_context` table (age/weight/renal/pregnancy/allergy fields) added to the schema with zero code path touching it yet.
**Gate (binary):** every Part-1 functional test passes against Postgres, with any DB-specific test adaptations (e.g. a SQLite-only assertion rewritten for Postgres semantics) explicitly documented in `DESIGN.md` rather than silently changed — the requirement is behavior-equivalence, not byte-for-byte-unchanged test files; the HTTP endpoint returns a correct Module C trace under 10 concurrent requests with zero errors; a static check confirms no arithmetic operation anywhere touches `patient_context` columns, extending Part 1's existing no-dosing guarantee to the new table from day one rather than retrofitting it later.
**Dependencies:** Postgres instance provisioned (DevOps) before migrations run.
**Ownership:** Tech Lead + AI agents write the port and service wrapper; DevOps provisions infra; Tech Lead personally reviews the no-dosing-fence check and every documented test adaptation.

### Week 2 — Real embeddings + concurrency/SLO measurement
**Deliverables:** `fastembed` enabled (production has no egress block); the 11-question mini-eval re-run against real embeddings; a load test across increasing concurrency to produce actual p95/p99 latency numbers.
**Gate (binary):** mini-eval accuracy on `fastembed` is ≥ the TF-IDF baseline (11/11) or every regression is individually explained in writing; a documented go/no-go decision on whether a request queue is needed, backed by the measured latency numbers against a stated SLO (per §1 — not assumed up front).
**Dependencies:** Week 1's service boundary.
**Ownership:** AI runs the embedding swap, eval re-run, and load-test harness; Tech Lead makes the queue go/no-go call — an architecture judgment, not automatable. Clinical SME starts corpus-sourcing conversations in parallel (does not block this week's gate).

### Week 3 — Review-queue triage UI + alias feedback loop + data-sourcing decisions
**Deliverables:** a minimal internal UI to list/filter/resolve `review_queue` items; an alias-feedback mechanism so a resolved item does not re-queue on the next ingestion run (closing `gaps_register.md` #5); a signed-off sourcing memo (which Indian sources, free/licensed/build, rough costs, rights terms).
**Gate (binary):** a human resolves a queued ambiguous item through the UI, and re-running ingestion against unchanged source data does not re-queue it; the sourcing memo names explicit costs and rights terms for every source it recommends.
**Dependencies:** Week 1 Postgres (concurrent writes).
**Ownership:** AI builds the UI/backend and the alias-propagation logic; Clinical SME makes the actual resolution judgment calls and source-vetting decisions — business/clinical judgment, not delegable to engineering.

### Week 4 — Multi-tenancy + freshness/re-evaluation pipeline + audit view
**Deliverables:** `tenant_id` scoping and row-level security across the schema; a data-version-triggered re-evaluation pipeline (a new gazette event flags affected prior rail results before any new result serves, satisfying binding law 10 — "no silent upgrades"); a queryable audit view.
**Gate (binary):** an adversarial test proves tenant B cannot read tenant A's rows under any code path attempted; injecting a new regulatory event into a demo tenant produces a re-evaluation flag on affected results before the next serve, with a test proving no silent staleness; an audit query correctly returns every check for a given doctor/date range.
**Dependencies:** Weeks 1–3 (stable schema, service boundary).
**Ownership:** AI implements RLS, the pipeline, and the audit view with tests; Tech Lead personally performs adversarial security review — multi-tenancy is exactly the kind of AI-generated code that needs a human actively trying to break it, not just green tests.

### Week 5 — Patient-context safety gating + corpus expansion + eval harness at scale
**Deliverables:** new deterministic contraindication checks (e.g. pregnancy/renal flags) under the same 8-state/provenance contract as the existing four; STW/national corpus expanded per Week 3's sourcing decision; the mini-eval harness scaled to a larger question set with a per-category (correct/abstained/wrong) breakdown, seeding the quality system in §6.
**Gate (binary):** every new contraindication check has a written specification authored and approved by the Clinical SME *before* implementation begins, passes the same test discipline as the existing four checks (8-state contract, provenance, no-HIT-as-safe), and carries the Clinical SME's sign-off against that specification before merge — with zero exceptions; the scaled eval harness runs end-to-end and produces the category breakdown.
**Dependencies:** Week 4 (stable multi-tenant schema), Week 3 (sourcing).
**Ownership:** **Clinical SME specifies and approves every contraindication rule — the clinical criterion, its trigger, and its evidence source are never engineering's or the AI's to define.** AI implements each rule strictly against the SME's written specification and ingests the expanded corpus; Tech Lead reviews implementation fidelity to the specification, not the clinical content itself.

### Week 6 — Load/chaos testing at target scale + comparison harness + pilot ramp-up
**Deliverables:** a sustained load test at 100 concurrent simulated doctors; a blinded BRAHMO-vs-ChatGPT/Claude comparison harness with a documented bias-mitigation protocol; a doctor onboarding pipeline exercised with real doctors; a final go/no-go review.
**Gate (binary):** the system sustains 100 concurrent users within the Week 2 SLO through a chaos drill (a node is killed mid-request) with zero data loss or tenant leakage; the comparison harness runs a blinded batch end-to-end against the documented protocol; the onboarding pipeline is demonstrated operational with real doctors flowing through it, explicitly measured against this plan's actual target — the assessment's own success condition (brief §6): **100 doctors, each submitting at least 1,000 real clinical questions, satisfaction measured against ChatGPT/Claude** — rather than a smaller stand-in number invented for this week; the go/no-go checklist confirms the system and harness are ready to run that exact test, and records the current onboarded-doctor count against the 100-doctor target as the plan's own measure of remaining ramp, not a new deliverable substituted for it.
**Dependencies:** all prior weeks.
**Ownership:** AI builds load/chaos-test automation and comparison-harness scaffolding; Clinical SME plus a doctor-relations contact (human) handle recruitment, onboarding, and blinding-protocol design — relationship and trust work that is not automatable by definition; Tech Lead owns the final go/no-go call.

## 3. Sources and data strategy

**Free / public**
- **CDSCO** (Central Drugs Standard Control Organisation) gazette notifications and Schedule H/H1/X listings — the same category of source `regulatory_gazette_events.csv` already represents in Part 1; free, but needs an ongoing scrape/ingest pipeline since it is published piecemeal, not as a clean feed.
- **NLEM** (National List of Essential Medicines) and **PMBJP/Jan Aushadhi** catalogs — already used in Part 1 at extract scale (63 and 50 rows respectively); the full published lists are free and would simply replace the extracts.
- **NPPA** (National Pharmaceutical Pricing Authority) price-control data — free; relevant to a future pricing/affordability feature, not core to safety.
- **ICMR and National Health Mission standard treatment guidelines** — free/public where issued as government guidance, expanding Module B's corpus beyond the 4 conditions covered today.

**Licensed**
- A **national-scale drug master**, the real-world equivalent of the 2,000-row CDCI subset used in Part 1. Realistic sourcing is a commercial Indian pharma database; we do not name or assume a specific vendor here, and we are not estimating a price — that requires a vendor quote we don't have. Treat this as an open procurement item, not a costed line.
- A **structured drug-interaction reference** at meaningfully greater depth than the 15-row severe-interaction seed list Part 1 was given. As with the drug master, we deliberately do not name or commit to a specific vendor or product here (see Gap #2 below) — what production needs is *adequate interaction-data depth and rights*, sourced through whatever procurement path clears legal/rights review at the time, not a single named database.
- **Specialty-society clinical guidelines** (e.g. pediatric or internal-medicine society guidance) — typically copyrighted publications even when publicly readable, so reproducing their content into decision-unit chunks needs explicit permission or a license, not just a web fetch. Rights terms are source-specific and not assumed here.

**Build / derived**
- **Disambiguation logic and UI** for the brand-name collision problem (see Gap #1 below) — our own engineering, no licensing question.
- **Condensed decision-unit chunks** derived from licensed/permitted guideline text, reviewed and signed off by the Clinical SME before ingestion — a derived work, not a raw republish, which is also the safer rights posture given the society-guideline copyright question above.
- **The alias/resolution feedback loop and the freshness/re-evaluation pipeline** (§1, §2 Week 4) — internal to our system, no external rights question.

We are not attaching a total cost figure to this section. The two licensed items above are the actual cost drivers and both require vendor quotes we don't have; putting a number on them here would be exactly the kind of claim the brief's own "claiming accuracy you did not measure" auto-fail condition warns against, applied to a plan instead of a result.

## 4. Gap analysis (≥3 concrete weaknesses in the provided materials)

Selected from `gaps_register.md`'s 13 entries as the most consequential for production, in order:

1. **Brand-name identity is ambiguous at the root.** 75% of CDCI rows (1,507/2,000) share a brand name with an unrelated formulation (gap #1) — different ingredients, strengths, sometimes different manufacturers. This is the most consequential weakness because everything downstream — the safety rail, retrieval filtering, doctor trust — assumes a resolved product identity. *What we'd do:* replace the current "queue and wait for a back-office reviewer" pattern with a doctor-facing disambiguation prompt at prescription-entry time — doctors know what they meant to prescribe faster than a reviewer can guess after the fact — and re-measure collision density against the full national catalog to determine whether this is a property of the 2,000-row subset or of Indian brand naming generally; we cannot tell which from inside the subset alone.

2. **The safety rail's negative results are honest but reference-data-starved.** 11 of 15 severe-interaction pairs and most regulatory-event targets never resolve against the 2,000-row CDCI subset (gaps #8, #9), so `severe_interaction` and `prohibited_restricted_fdc` return `PARTIAL_COVERAGE` on nearly every prescription instead of a clean `CHECKED_NO_HIT`. This is the most consequential *safety* gap: the rail correctly refuses to overclaim rather than guessing, but a reference-data-starved rail provides limited real protection. *What we'd do:* treat broader reference-data coverage — both a larger drug master and a deeper interaction reference — as a **production dependency to resolve**, not a specific vendor to mandate; no amount of engineering closes a gap that is rooted in reference-data size, and the actual sourcing path (which vendor, what rights, what it costs) is a procurement decision for closer to the time, informed by whatever passes legal/rights review then.

3. **Pharmacy-stock intake fails at scale.** 574 of 783 real pharmacy rows (73%) cannot be uniquely resolved (gap #2), mostly for the same brand-collision reason as #1 (554 ambiguous, 20 no match at all). *What we'd do:* the same disambiguation-UI fix as #1, plus re-measuring against the full national catalog to separate "subset too small" from "genuinely ambiguous real-world data" — again, not distinguishable from inside this subset.

4. **Auto-resolved items are never re-validated as the drug master grows.** A brand that resolves uniquely today can become ambiguous the moment a later ingestion adds a colliding product, and nothing currently detects this (gap #6). This risk doesn't manifest in Part 1's one-shot ingestion but becomes live the moment a production catalog updates on a schedule. *What we'd do:* this is precisely what the freshness/re-evaluation pipeline (§1, §2 Week 4) exists for — a new ingestion batch should re-check prior auto-resolutions against the updated candidate set, not just add new rows on top.

## 5. The doctor's reality

- **Alert fatigue.** On Part 1's own data, `severe_interaction` and `prohibited_restricted_fdc` return `PARTIAL_COVERAGE` on nearly every prescription (gaps #8/#9), indistinguishable at a glance from a clean `CHECKED_NO_HIT` if surfaced carelessly. *Decision:* the doctor-facing rendering must visually separate "checked, nothing found" from "coverage incomplete, use judgment" — never collapse both into a single green checkmark. *Why:* a doctor who sees `PARTIAL_COVERAGE` treated as "safe" often enough will learn to ignore the rail entirely, which is a worse outcome than no rail at all. *Rejected alternative:* hiding `PARTIAL_COVERAGE` behind an "advanced details" toggle to reduce visual noise — rejected because it silently converts unknown into safe-looking, precisely what binding law and the auto-fail conditions forbid. *Implication:* the UI design in §1/§2 needs this distinction built in from the first screen, not patched on later.
- **Trust and speed.** Module B answers are retrieval-and-quote only (no generation), which is slower to read and less conversational than ChatGPT/Claude's synthesized prose, and a doctor comparing the two head-to-head (the actual 100-doctor test) will notice. *What the plan does about it:* the comparison harness (§6) must let the fairness question be examined honestly — grounded-but-terser vs. fluent-but-ungrounded is the real trade-off being tested, and the plan should not assume BRAHMO wins on "feel."
- **Unanswerable questions.** Today's corpus covers 4 conditions; the 11-question mini-eval already includes 2 questions that correctly abstain (migraine, TB) because the corpus doesn't support them. At the scale of "1,000 real questions per doctor," most questions will fall outside even an expanded corpus. *What the plan does about it:* clean, fast abstention with a stated reason is the product, not a failure mode — this is already Part 1's design discipline (G6, clean abstention), and it needs to hold under real question volume rather than erode under pressure to "always answer something."
- **Language.** Part 1's corpus and all code are English-only; no vernacular-language handling exists anywhere in the current system. This is an honest, currently-unaddressed gap for a system meant for doctors across India, and is called out explicitly as a fence in §8 rather than assumed away.
- **Workflow interruption.** Module C today is a CLI script; there is no doctor-facing surface at all. Every claim in this section about "what a doctor sees" describes a UI that does not yet exist and is scoped for construction across §2's six weeks — this is stated plainly so it isn't read as already solved.

## 6. The quality system

**Operational definition of "excellent" for the 100-doctor test:** the same three-way verdict Part 1's mini-eval harness already uses — correct / abstained / wrong — applied per-question, per-doctor, at scale, plus the G6 structural check (every consequential number traceable verbatim to a cited source) run on 100% of answers automatically, since it's a deterministic string check, not a judgment call.

- **Decision:** scale the existing mini-eval harness pattern (already proven at 11/11 in Part 1) rather than designing a new evaluation framework for production. **Why:** the harness's scoring logic (state match + citation match + verbatim-text match) is already implemented, tested, and its failure modes are understood from the five debugging rounds it took to get right in Part 1 — reusing it is lower-risk than a fresh design. **Rejected alternative:** a purely human-graded pilot with no automated scoring — rejected because it can't run at "1,000 questions × 100 doctors" volume without becoming the "100,000 manual reviews" problem this section exists to avoid. **Implication:** every new question category added during the 6-week plan (§2 Week 5's expanded corpus) needs its own harness-scorable expected answer, the same discipline `sample_questions.py` already follows.

**Release gate (per deploy):** no release ships if it regresses the mini-eval's correct/abstained/wrong distribution versus the last approved baseline, and G6 (verbatim citation) must be 100% clean — this mirrors Part 1's own acceptance-gate structure (G1-G7) rather than inventing new criteria.

**100,000 answers without 100,000 manual reviews:** two tiers. Automated (100% of traffic): the G6 verbatim-citation check and 8-state contract validation, both deterministic and already implemented in Part 1. Human-sampled (a stratified subset, not a fixed number we haven't measured): Clinical SME review concentrated on `ABSTAINED` and `PARTIAL` verdicts and any `wrong` verdicts the harness catches, since those are where a real clinical judgment call is needed — a clean `correct` verdict with clean citations needs no human re-review, it's already been checked structurally.

**Fair BRAHMO vs. ChatGPT vs. Claude comparison:**
- **Decision:** blinded presentation — the doctor sees two or three anonymized answers to their own real question and rates them without knowing which system produced which. **Why:** doctors have prior brand familiarity with ChatGPT/Claude; an unblinded comparison measures brand trust, not answer quality. **Rejected alternative:** an unblinded side-by-side (BRAHMO clearly labeled) — rejected because it can bias the rating in either direction depending on the doctor's prior opinion of "an AI built for this specific purpose" vs. "a general assistant," and we have no way to separate that bias from genuine quality difference after the fact. **Implication:** the pilot infrastructure (§2 Week 6) needs a randomized, order-varied presentation layer, not just three API calls side by side.
- The comparison must be run on the doctor's own real questions, not a curated question set — otherwise it measures performance on questions chosen to flatter one system.

## 7. Dependencies and critical path

What actually gates the timeline, named explicitly because none of it is code:

- **Clinical SME availability.** At ~20% time, the SME is the sole approver of every contraindication rule (§2 Week 5) and every corpus-expansion source (§3). If SME bandwidth slips, Week 5's gate slips with it — this is the single most likely critical-path bottleneck in the whole plan, precisely because it is deliberately not delegated to AI or engineering.
- **Data licensing and rights clearance** (§3, §4 gap #2). Procuring a national-scale drug master and a deeper interaction reference involves vendor negotiation and legal rights review — neither is estimable in duration from inside this repo, and both sit upstream of Week 5's corpus-expansion and reference-data-coverage work.
- **Doctor recruitment for the pilot** (§2 Week 6). Reaching real doctors, getting their consent, and onboarding them into a blinded comparison is a relationship-building process on a timeline outside engineering's control.
- **Infrastructure provisioning** (Postgres, load-test environment, row-level security config) — a DevOps/ops dependency with external lead time (procurement, access approvals) that Week 1 and Week 4 depend on.
- **Security/rights review of any reproduced guideline text** — before any specialty-society guideline content is ingested into the corpus, it needs legal sign-off that the derived decision-unit chunks (§3) don't infringe the source publication's rights.

## 8. Fences — what this version will NOT build

Each fence below is a decision carried forward from Part 1's own binding laws, not a new cut invented for Part 2.

- **No patient-specific dose calculator, ever.** *Why:* binding law in Part 1, enforced structurally (no arithmetic operator touches Module B's answer text, AST-verified) and explicitly re-affirmed in §1 as patient context is added — patient data may gate a safety check, never feed a dose computation. *Rejected alternative:* a "doctor confirms before use" soft gate around a computed suggested dose — rejected because it is exactly the auto-fail condition ("a patient-specific dose calculator") regardless of a confirmation step wrapped around it.
- **No LLM anywhere in the safety-check path.** *Why:* Part 1's rail is pure deterministic lookup logic by design; this stays true at any scale, since the risk an LLM introduces (a plausible-sounding wrong answer) is precisely what a safety rail exists to prevent.
- **No diagnosis.** This version answers grounded clinical-workflow questions and checks prescriptions against known drug/regulatory data; it does not attempt to diagnose a patient from symptoms — out of scope for the stated 6-week production goal, not attempted.
- **No vernacular/multi-language support.** Part 1's corpus and code are English-only; adding real vernacular-language clinical grounding (not just UI translation) is a corpus-sourcing and clinical-review effort of its own scale, deliberately deferred past this version rather than bolted on superficially.
- **No fuzzy-match auto-accept.** Part 1 deliberately implemented only exact-normalized-string matching with everything else queued (D-002); this version keeps that discipline rather than adding a confidence-threshold auto-accept to reduce review-queue volume, since that is the exact failure mode (a confident wrong match) the brief's held-back scoring penalizes hardest.
- **No monetization, billing, or multi-tenant admin/plan-management layer.** Multi-tenancy (§1, §2 Week 4) is built for data isolation between clinics, not for a commercial multi-tenant SaaS product — billing, plan tiers, and tenant self-service administration are out of scope for reaching the 100-doctor test.
