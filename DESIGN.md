# DESIGN.md — Shantanu Sahu

## 0. The system in my own words (one paragraph)

BRAHMO is a doctor-facing clinical AI for Indian outpatient practice that is patient-aware, cites its sources, and never lets a language model touch a medication-safety decision. Part 1 proves the two load-bearing pieces underneath that promise: a versioned, event-sourced drug master that can decompose any Indian brand-name product (including fixed-dose combinations) down to its constituent salts without ever silently guessing an ambiguous mapping, and a deterministic rail that runs safety checks over that decomposition using pure lookup logic. This slice of the build (Module A ingestion/normalization) proves the first half: every row of the provided data pack is loaded with full source/version/batch provenance, all 160 FDC products are decomposed into individually-versioned ingredient rows, and every mapping that cannot be made with certainty — which turns out to be the majority of real-world pharmacy stock — lands in an auditable review queue with a reason code and evidence, never a guess.

## 0.1 The three riskiest assumptions I see in the provided materials

1. **That "brand name" is a usable identity key at all.** 565 of 1,058 distinct brand names in the CDCI subset (75% of product rows) are shared by two or more completely unrelated formulations — different ingredients, different strengths, sometimes different manufacturers ("Becet 1" is both Sertraline 100mg and Cefixime 100mg). Any design that resolves a doctor's typed or scanned brand name to "the product" without also disambiguating by strength, manufacturer, or an explicit doctor confirmation is building on sand. I treat this as the single highest-risk assumption in the whole packet — worth confirming with BRAHMO whether the real, non-subset CDCI data has this same density of collisions, because if so it reshapes the entire prescription-intake UX (the doctor must always be shown and asked to confirm which formulation, not just which brand).
2. **That a 2,000-row CDCI subset is representative enough to validate against real pharmacy stock.** 574 of 783 real pharmacy_stock.csv rows (73%) cannot be uniquely resolved against this subset — 554 because the brand name is ambiguous within the subset itself, 20 because there's no exact match at all. Some of that 20 is very plausibly coverage gaps (real brands that exist in the full national dataset but were cut when this 2,000-row subset was prepared for the assessment), not genuine real-world ambiguity. I can't tell the two apart from inside the subset, and neither should the system pretend to.
3. **That fuzzy/AI-assisted matching is a productivity aid rather than a load-bearing decision.** It's tempting to raise the auto-accept threshold once you see a fuzzy match scoring 88.9% similarity ("CMOX" → "Camox"). I deliberately did not build any fuzzy auto-accept tier at all (see D-002) because in a drug-identity context a wrong 88.9%-confidence guess is not "close enough," it's a different drug. This is a bet that BRAHMO's tolerance for review-queue volume is higher than its tolerance for a single wrong auto-resolution — worth confirming, since the review queue this run produced is not small (577 items from Module A ingestion alone).

## Decisions

### D-001 — brand_name is not a unique key in the products table
- **Decision:** `products.external_product_id` (CDCI's own `CD1000`-style id) is the sole identity key. `brand_name` and its normalized form are indexed for search but carry no uniqueness constraint.
- **Why:** The data itself falsifies brand-name uniqueness — 75% of product rows share a brand name with an unrelated formulation. A schema that assumed uniqueness would either reject valid CDCI rows or silently merge distinct drugs into one identity.
- **Rejected alternative(s):** (a) `UNIQUE(brand_name)` with a "most recent wins" or "first wins" tiebreak on conflict — rejected outright, this is exactly the silent-guessing failure mode the brief calls out as an auto-fail. (b) `UNIQUE(brand_name, manufacturer)` — rejected because it still collides for 77 brand names in this subset; it narrows the problem without solving it.
- **Implication:** Every downstream consumer of `products` (the future safety rail, Module B's structured-fact lookups, prescription intake) must query by `external_product_id`, never assume a brand-name lookup returns one row, and must handle the multi-row case explicitly.

### D-002 — no fuzzy auto-accept tier; only exact-normalized-match may auto-resolve
- **Decision:** Resolution confidence has exactly two useful tiers: `structured_source_field` (1.0, the source declares the mapping itself) and `exact_normalized_match` (0.9, a case/whitespace/hyphen-normalized exact string match against a single existing candidate). Anything that required approximate/fuzzy matching — `fuzzy_candidate_unconfirmed` — is always queued, regardless of similarity score.
- **Why:** A single numeric confidence threshold (e.g. "auto-accept fuzzy matches ≥ 90") invites exactly the failure the brief warns about: a confident wrong answer. I found a real case in the data ("CMOX" → "Camox", rapidfuzz WRatio 88.9) where a plausible-looking threshold would auto-accept a match to one of two entirely different drugs (Ibuprofen or Nitrofurantoin) sharing that brand stem.
- **Rejected alternative(s):** A single `fuzzy_match_min_score` threshold for auto-accept (my own first draft, before I ran the data and saw the collision above) — rejected once measured against the actual data, not a hypothetical.
- **Implication:** The review queue volume from real-world input (pharmacy stock, in this case) will be large — 574/783 rows in this run. That's a UX and staffing problem for Part 2 (see gaps register), not a bug in Module A; I'd rather surface that cost honestly than hide it behind a threshold tuned to look clean on this one file.

### D-003 — product_resolutions is a separate table from review_queue
- **Decision:** Every resolution *attempt* (auto-resolved or queued) is logged to `product_resolutions` with its full candidate set. `review_queue` holds only the subset that needs a human, referencing back to the same entity.
- **Why:** "100% provenance on data rows and check results" (gate G5) requires being able to answer "why was this auto-resolved?" for the 209 rows that were, not just "why is this queued?" for the 574 that weren't. Folding both into one table would force awkward nullable columns and blur the audit trail.
- **Rejected alternative(s):** A single table with a `status` column and no distinction — rejected, it's cheaper to build but answers fewer audit questions later.
- **Implication:** Any report on ingestion quality (e.g. "what fraction of pharmacy stock did we resolve confidently?") is one query against `product_resolutions`; any work queue for a human reviewer is one query against `review_queue`. They can evolve independently.

### D-004 — ingredient_aliases is a first-class table, separate from product_ingredients
- **Decision:** Ingredient-name normalization (matching salt-name spelling variants, e.g. NLEM's "Amoxicillin + Clavulanic Acid" against CDCI's split ingredient columns) has its own audit table, distinct from the product→ingredient decomposition table.
- **Why:** These are different problems with different failure modes. FDC decomposition (product_ingredients) is "which salts and strengths make up this specific product." Ingredient normalization (ingredient_aliases) is "is this string the same molecule as that string." Conflating them would make it impossible to answer "how did we decide Paracetamol and paracetamol are the same ingredient" separately from "how did we decide Sinarest contains paracetamol."
- **Rejected alternative(s):** Storing a raw ingredient string directly on `product_ingredients` with no separate alias table — rejected, it would mean re-deriving the alias decision from scratch every time instead of reusing an audited one.
- **Implication:** New sources that mention ingredients by name (Module B's clinical text, eventually) can resolve against the same alias table and inherit the same "exact vs. queued" discipline.

### D-005 — SQLite for Part 1, with numbered raw-SQL migrations rather than an ORM/Alembic layer
- **Decision:** Schema ships as 10 numbered, hand-written `.sql` migration files (`db/migrations/0001_...` through `0010_...`), applied by a ~30-line runner that tracks applied filenames in a `schema_migrations` table.
- **Why:** At this data volume (2,000 products, ~800 pharmacy rows) a full ORM/Alembic setup is overhead that makes the schema *harder* to review, not easier — a reviewer can read every migration file top to bottom in a few minutes. SQLite needs zero setup for the "<1 hour fresh-machine reproduction" gate.
- **Rejected alternative(s):** SQLAlchemy models + Alembic autogeneration — rejected for this phase as premature structure; Postgres — rejected for Part 1 as an unnecessary dependency, though SCALE.md flags this as the first thing to change at higher concurrency.
- **Implication:** Migrations are plain SQL, so they're portable to Postgres later with minimal translation, but nothing here optimizes for that yet.

### D-006 — content-hash idempotency for every Module A loader
- **Decision:** Every loader (`load_cdci`, `load_nlem`, `load_jan_aushadhi`, `load_pharmacy_stock`) computes a SHA-256 hash of the source file's bytes before doing anything else. If a `load_batches` row already exists with the same `(source_name, file_hash)` and `status='COMPLETE'`, the loader inserts nothing and returns the existing counts with `skipped: True`.
- **Why:** Design review surfaced that re-running ingestion against the same files duplicated every table Module A writes to — products, pharmacy items, ingredient aliases, and review queue entries all doubled on a second run. That's not a trade-off, it's a defect: a reviewer following the README's fresh-machine steps twice, or a retry after an unrelated failure, would have silently corrupted the drug master.
- **Mandated or preference:** Not explicitly required by the brief. It follows directly from binding law 8 ("everything versioned, everything replayable") and from ordinary engineering hygiene for anything reproducibly re-run — I'd call this closer to a correctness bug fix than a design preference.
- **Rejected alternative(s):** A DB-level `UNIQUE(source_name, file_hash)` constraint — rejected because it would also block a legitimate retry after a `FAILED` batch (the constraint can't distinguish "already succeeded" from "previously failed, try again") without extra conditional-index complexity that isn't worth it at this scale. An explicit `--force` CLI flag requirement instead of automatic detection — rejected as more error-prone for a reviewer running the README as written, who has no reason to know a flag exists.
- **Trade-offs/risks:** The hash check is keyed on byte-for-byte file content. A source file that's semantically identical but re-saved with different line endings or whitespace would hash differently and re-ingest — acceptable for this assessment; worth a content-normalization step before hashing if this were long-lived.
- **Implication:** `run_all.py` is now safe to run repeatedly; the new `test_full_pipeline_run_twice_is_stable` test pins this directly.

### D-007 — file_hash is the provenance identity for sources with no declared version
- **Decision:** `pharmacy_stock.csv` has no version or date column of any kind. Rather than inventing a synthetic `source_version` value, `pharmacy_stock_items.source_version` stays `NULL`, and `load_batches.file_hash` (added for D-006) is the actual identity a reviewer or auditor should use to answer "which exact data produced this row."
- **Why:** A fabricated version string (e.g. a made-up date, or "v1") would look like real provenance without being one — worse than an honest NULL, because it invites false confidence that the source declared something it didn't.
- **Mandated or preference:** The instruction not to invent a fake version was an explicit engineering decision from design review, not from the brief. The brief requires "source, source version/date, and load batch" per row (§4); this decision interprets that as "record what's actually true," including the true fact that some sources declare no version.
- **Rejected alternative(s):** Synthesizing a version from the load timestamp (rejected — that's a property of *when we loaded it*, not a property of the data itself, and conflating the two is exactly the kind of confidence gate 5 is meant to prevent); requiring every source to declare a version before it can be ingested (rejected — would make it impossible to ingest `pharmacy_stock.csv` at all, which is core to the assessment).
- **Trade-offs/risks:** Any downstream code checking `source_version IS NOT NULL` as a completeness signal must know this is an expected, permanent NULL for this source, not a bug — documented in the gaps register and in code comments, but only a comment away from being misread.
- **Implication:** `product_resolutions` and `review_queue` rows referencing `pharmacy_stock_items` can still be traced to the exact ingestion run via `load_batch_id` → `load_batches.file_hash`, even though no human-readable version string exists for this source.

### D-008 — unresolved confidence is NULL, not 0.0
- **Decision:** `ingredient_aliases.confidence` is nullable; `fuzzy_candidate_unconfirmed` rows now store `NULL` instead of the previous `0.0` sentinel.
- **Why:** `0.0` is a real, meaningful confidence score (would mean "resolved, with zero confidence in the resolution"); `NULL` means "not resolved, no confidence value applies." Conflating the two made any future aggregate query over confidence (e.g. average confidence per source) silently wrong by counting unresolved rows as zero-confidence data points.
- **Mandated or preference:** My own fix, flagged during design review as an inconsistency against `product_resolutions.confidence`, which already used NULL correctly for the equivalent case.
- **Rejected alternative(s):** Leaving `0.0` and documenting the convention instead of fixing it — rejected as the cheaper but wrong choice; a schema-level fix removes the footgun rather than just labeling it.
- **Trade-offs/risks:** Required a migration that recreates `ingredient_aliases` (SQLite can't drop a `NOT NULL` constraint in place). Migration 0012 does this via the standard create-copy-drop-rename pattern and maps any pre-existing `0.0` values to `NULL` via `NULLIF` during the copy, so this is also safe to apply to a database that already has rows from before this change.
- **Implication:** Any code (now or in Module B) that treats "confidence" as a plain float must handle `NULL` explicitly rather than assuming a number is always present.

### D-009 — event-sourced regulatory status is resolved by "latest effective_date <= as_of", not by walking supersedes_event_id
- **Decision:** `regulatory_events` is an append-only log (A.5). Current status for a target ingredient/FDC set as of a given date is computed by grouping events with the same *parsed* target (ingredient-name set + target_type) and taking the action of whichever event has the latest `effective_date <= as_of_date`. `supersedes_event_id` is stored and returned as evidence/lineage but is NOT used to compute the answer. Two events tied at the same latest `effective_date` with different actions is reported as `SOURCE_CONFLICT` rather than picking one arbitrarily.
- **Why:** This data pack's own EV001→EV002→EV003 chain (2018 ban → 2019 court stay → 2023 re-ban) proves the naive alternatives wrong: "first event wins" misses the re-ban; "most recent event by insertion order" is fragile; only "true chronological effective status" is correct, and it falls out for free from a plain `MAX(effective_date)` query without needing to interpret what each `action` value means relative to its predecessor.
- **Mandated or preference:** The brief requires the regulatory check to be event-sourced and to never render missing/stale data as safe. The specific resolution algorithm is my own design.
- **Rejected alternative(s):** Walking `supersedes_event_id` as a linked list to find "the current head" — rejected because it requires trusting that the source data's `supersedes_event_id` links are complete and correctly directed, which is an extra assumption about data integrity that a plain latest-effective-date query doesn't need. Treating `STAY_GRANTED` as a special action that "reverts" to some other computed status — rejected as unnecessary complexity; it works correctly as just another action a target can currently have.
- **Trade-offs/risks:** If a future data pack ever has a genuinely non-chronological correction (e.g., a legally backdated notification published after an intervening one takes effect), `effective_date`-only resolution could disagree with `supersedes_event_id`. Not observed in the provided data; would show up as a mismatch between "current status" and "the event pointed to by the latest sibling's supersedes_event_id" and is worth an assertion if this were long-lived.
- **Implication:** Scope qualifiers (see D-009 continuation below) and target-ingredient mapping happen once per event at ingestion time (`target_parser.py`), so the status-resolution query itself stays a simple, auditable date comparison.

### D-009(b) — scope qualifiers: verify what's structurally verifiable, flag the rest, never assert or drop silently
- **Decision:** `target_description`'s trailing parenthetical (e.g. "(paediatric suspensions only)", "(Schedule H1 enforcement)") is classified into exactly three buckets: `UNLIMITED` (no qualifier, or "all strengths"/"all products"), `SUSPENSION` (checked deterministically against the matched product's own `dose_form` column — the one qualifier this system has a structured field to verify), and `UNVERIFIABLE` (everything else — rendered as `PARTIAL_COVERAGE` with the qualifier quoted, never a bare HIT and never silently dropped).
- **Why:** Blindly matching on ingredients alone would have produced a HIT for Combiflam (a Tablet) against EV012, whose own note says "adult tablets unaffected" — a false positive the source data itself explicitly disclaims. Blindly ignoring any qualifier would have missed EV008's real dispensing restriction on Tramadol.
- **Mandated or preference:** My own design, filling a gap the finalized Safety Rail decisions didn't specify. Flagged explicitly to BRAHMO for review rather than treated as pre-approved.
- **Rejected alternative(s):** Ignoring scope qualifiers entirely and matching on ingredients only — rejected, produces the Combiflam false positive above. Attempting to parse patient age / formulation intent from `clinical_note` or elsewhere to resolve every qualifier — rejected as guessing beyond what the data actually supports.
- **Trade-offs/risks:** Any qualifier this system can't structurally verify degrades a specific, real regulatory match to PARTIAL_COVERAGE rather than HIT — a human must still read the evidence and decide. This is intentional (see gap 11) but means the check is deliberately less "decisive" than a system willing to guess.

### D-010 — a check's coverage can never be claimed complete while any of its source data is unmatchable
- **Decision:** For both the prohibited/restricted-FDC check and the severe-interaction check, a "no hit found" result is `CHECKED_NO_HIT` only if every row of the relevant source data (regulatory_events' target ingredients; severe_interaction_seed's ingredient pairs) successfully resolved to a canonical ingredient. If ANY row anywhere in that source is unmappable/unresolved, every negative result from that check — regardless of which prescription — is `PARTIAL_COVERAGE` instead.
- **Why:** Verified against the real data pack: 3/12 regulatory events and 11/15 interaction-seed rows have at least one ingredient that never resolves against this CDCI subset's vocabulary (see gaps register #8–9). Claiming `CHECKED_NO_HIT` on any prescription while that's true would be asserting completeness the system does not actually have.
- **Mandated or preference:** Directly derived from the binding law "missing data must never render as safe," applied at its most literal.
- **Rejected alternative(s):** Scoping the completeness check per-prescription instead of globally (i.e., only downgrade to PARTIAL_COVERAGE if the *specific* unmatched row's ingredient plausibly relates to *this* prescription) — considered and rejected for this pass: determining "plausibly relates" for an ingredient we by definition can't identify is circular. The global rule is more conservative but the only one that doesn't require guessing.
- **Trade-offs/risks:** This is a strong, visible consequence: on the current data pack, `CHECKED_NO_HIT` is unreachable for these two checks — every negative result is PARTIAL_COVERAGE. That's an accurate reflection of this subset's coverage, but it means the demonstration set has no example of a "clean negative" from these two checks. Worth deciding whether that's acceptable for the submission or whether a fuller ingredient vocabulary (beyond this 2,000-row CDCI subset) should be sourced before the defense.
- **Implication:** A duplicate_active_ingredient HIT is unaffected by this rule (it depends only on CDCI's own decomposition, which has no analogous unmapped-row problem).

### D-011 — no dose-limit threshold exists or is invented; cumulative exposure is evidence, not a verdict
- **Decision:** The duplicate-active-ingredient check triggers a HIT purely on presence (the same ingredient decomposed out of 2+ distinct products in one prescription). The cumulative per-ingredient daily total is always computed and attached as evidence on that HIT, but no maximum-safe-daily-dose threshold is applied to it, and none is invented.
- **Why:** Confirmed by direct inspection (at the user's explicit request, before this implementation began) that no source in the provided data pack — not CDCI, not the local clinic protocol, not any other file — supplies a numeric daily-dose ceiling for any ingredient. The brief's own wording for this check ("a duplicate-ingredient HIT must carry this aggregate as its evidence") already describes exactly this shape: total-as-evidence, not total-as-verdict.
- **Mandated or preference:** This was the user's explicit, final engineering decision for Check 4, made after reviewing the actual data.
- **Trade-offs/risks:** An item whose `dose_frequency` doesn't parse (e.g. "SOS") is excluded from the numeric total rather than assumed to contribute zero — the total is marked `cumulative_is_partial: true` and the excluded item is named explicitly, so the gap is visible rather than silently absorbed into a falsely-precise number.

### D-012 — PRODUCT-type regulatory targets and free-text-only product names are out of automated scope
- **Decision:** `regulatory_events` rows with `target_type='PRODUCT'` are ingested (nothing is dropped) but not matched by the automated prohibited/restricted-FDC check. Every check in the rail reports this explicitly in its negative-result evidence (`product_type_events_out_of_scope`).
- **Why:** Matching a free-text product description (e.g. "Ofloxacin + Ornidazole Suspension (paediatric)") to a specific CDCI `product_id` would require fuzzy/approximate text matching against a safety-critical regulatory action — exactly the "confident wrong answer" risk D-002 already rejected for ordinary drug-identity resolution, at higher stakes.
- **Rejected alternative(s):** Fuzzy-matching PRODUCT-type descriptions against `products.brand_name`/`strength_text` — rejected for the reason above. Treating any regulatory PRODUCT event as applying to nothing and dropping it entirely from ingestion — rejected; the event is real data and stays queryable even though this check doesn't act on it automatically.
- **Implication:** See gaps register #10.

### D-013 — a rail check's untrusted written_product input is resolved analytically, not through the ingestion review_queue
- **Decision:** `resolve_prescription_item` (used by all three rail checks) applies the same exact-match-only-auto-resolve discipline as `pharmacy_matcher.resolve_pharmacy_item`, but an unresolved item is surfaced directly in that check's own result (`UNVERIFIED_INPUT` state, or noted in a `PARTIAL_COVERAGE`/`HIT` result's evidence) rather than written to the `review_queue` table.
- **Why:** `review_queue` (D-003) exists to track uncertain *ingestion* mappings that persist as durable data and get resolved once, by a human, independent of any particular query. A rail check run is an analytical read against already-ingested data, not a new ingestion event — there is no natural persistent row for "item 2 of RX04 as evaluated on 2026-09-27" to attach a queue entry to, and forcing one in would blur the audit trail D-003 was built to keep clean.
- **Rejected alternative(s):** Creating a `seed_prescription_items` table purely so unresolved rail inputs have somewhere to be queued — rejected as schema overhead for data that isn't actually being ingested/reused, when the 8-state vocabulary (`UNVERIFIED_INPUT` in particular) already exists to carry exactly this meaning at the check-result level.
- **Implication:** An unresolved prescription item is fully visible in the rail's own persisted output (`rail_check_results.evidence_json`), just not in `review_queue`. A future Part 2 UI surfacing "items needing review" would need to read both tables, not just one.
